Lesson 01: First Dialogue — Goodbye to Hardcoded Nightmares

Problem and Observable Goal

Problem: A character has no dialogue yet.

By the end: Show three lines and reset after the last confirmation.

Lesson Goals

In about five minutes, you will get a game character talking. We use the most direct path first—then we tear it down on purpose and ask the question that matters: why do we need something better?

Step 1: Build the Simplest Stage

1.1 Create a Basic Scene

  1. Open Godot and create a new project (or use an existing one such as godot_simple_arpg_demo).
  2. Create a 2D scene with root node Main (or 3D if that matches your game).
  3. Add a Sprite2D (2D) or MeshInstance3D (3D) as the player. Name it Player.
  4. Under Player, add a Label (2D) or Label3D (3D) for dialogue text. Name it DialogueLabel.

Scene tree:

- Main (Node2D or Node3D)
  - Player (Sprite2D or MeshInstance3D)
    - DialogueLabel (Label or Label3D)

1.2 Configure the Label

2D: Select the Label. In the Inspector:

  • Text: leave empty (set in code)
  • Horizontal Alignment: Center
  • Vertical Alignment: Center
  • Autowrap Mode: Word Smart (optional, for long lines)

3D: Select Label3D:

  • Text: empty
  • Billboard: Enabled
  • No Depth Test: on (reduces occlusion issues)

Step 2: A One-Off Dialogue Script

Attach a new script to Player, name it player.gd, and paste:

# player.gd
extends Sprite2D  # For 3D, use MeshInstance3D and change the label type to Label3D

# 1. Hardcode all lines in an array
var dialogue_lines: Array[String] = [
	"Hello, adventurer.",
	"This world needs your help.",
	"Ready to set out?"
]

# 2. Track which line we are on
var current_line_index: int = 0

@onready var dialogue_label: Label = $DialogueLabel

func _ready() -> void:
	dialogue_label.hide()

# 3. Listen for global input
func _unhandled_input(event: InputEvent) -> void:
	if event.is_action_pressed("ui_accept"):
		if not dialogue_label.visible:
			dialogue_label.show()
			dialogue_label.text = dialogue_lines[current_line_index]
			current_line_index += 1
			return
		
		if current_line_index < dialogue_lines.size():
			dialogue_label.text = dialogue_lines[current_line_index]
			current_line_index += 1
		else:
			dialogue_label.hide()
			current_line_index = 0

2.1 Code Walkthrough

  1. dialogue_lines — stores all text. Easy to read, but this is where pain starts at scale.
  2. current_line_index — advances each time the player confirms.
  3. @onready var dialogue_label — Godot initializes this reference when the node becomes ready, before calling its _ready() method.
  4. _unhandled_input() — ui_accept is the default confirm action (Enter / Space).
  5. Flow: first press shows line 1; later presses advance; after the last line, hide and reset.

2.2 Run It

Press F5. Hit Enter or Space. Lines appear one by one. It works—and that is exactly the trap.

Step 3: Judge the Code We Just Wrote

Before celebrating, imagine hundreds or thousands of lines, many NPCs, and player choices. What breaks?

This section is the core of the lesson: name the problems.

3.1 Hard to Maintain

Scenario: 500 lines in the array; you need to fix a typo on line 237.

Reality: you hunt through logic to find one string.

Cost: every copy change touches code, re-run risk, and merge noise.

3.2 Not Reusable

Scenario: another NPC needs the same lines.

Reality: copy-paste.

Cost: DRY violations—fix in one place, forget another, ship a bug.

3.3 No Branching

Scenario: after “Ready to set out?”, offer “I’m ready” vs “I need more prep.”

Reality: nested if/else spaghetti.

if current_line_index == 2:
	if player_choice == "ready":
		dialogue_lines = ["Great, let's go!", "..."]
	else:
		if player_has_item("sword"):
			dialogue_lines = ["Go prepare first.", "..."]
		else:
			dialogue_lines = ["You need a sword.", "..."]
# ... more nested if-else ...

Cost: in three months, you will not trust this file.

3.4 Tight Coupling of Data and Logic

Root issue: story text and display logic live in one script.

Requiring writers to edit gameplay scripts creates unnecessary friction. Content and behavior cannot version cleanly. Production slows down.

Step 4: Architecture Mindset

What we built is a fragile prototype. Fine for a five-minute test; wrong as the foundation of a narrative engine.

4.1 What Good Looks Like

  1. Separate data from logic — text in external files; code reads and presents.
  2. Extensible — branches, conditions, actions without rewriting the core.
  3. Maintainable — non-programmers can author content.
  4. Reusable — one system for every NPC and scene.

4.2 Where We Go Next

Next lesson we replace this design with data-driven structure: JSON for content, code for interpretation, config for branches, conditions, and actions.

Exercise and Completion Check

Replace the three lines with your own introduction, then play through it twice.

Done when: Both runs display the same three lines in order and hide the label afterward.

Lesson Summary

Takeaways

  • Hardcoding is valid for fast prototypes.
  • You can spot architectural limits before they ship.
  • Data/logic separation is non-negotiable for real narrative tools.

Terms

  • Hardcoding — data embedded in source.
  • Coupling — how tightly modules depend on each other.
  • Data-driven — behavior driven by external data.
