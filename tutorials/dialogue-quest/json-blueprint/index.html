Lesson 02: The Script Blueprint — JSON Data Structure Design

Problem and Observable Goal

Problem: Hardcoded text cannot express a reusable dialogue graph.

By the end: Identify text, choices, and next-node IDs in one JSON file.

Lesson Goals

Internalize data-driven design and lock in the system’s data contract—the JSON shape that every later feature will build on.

Step 1: Data-Driven Design

1.1 Definition

Data-driven design means: volatile content (dialogue, stats, level config) lives outside code. Code loads and interprets; data drives behavior.

1.2 Why It Matters

Lesson 01 problems:

  • Hardcoded strings
  • Writers blocked on programmers
  • Features require core rewrites

Data-driven wins:

  • Edit JSON without recompiling
  • Parallel work for narrative and engineering
  • Extend via schema, not spaghetti
  • Clean git history for content vs code

Step 2: Why JSON?

We store scripts in JSON.

2.1 Strengths

  1. Human-readable
  2. Tree-shaped—fits branching dialogue
  3. Godot’s JSON API is first-class
  4. Editor tooling (VS Code validation, highlighting)

2.2 Alternatives

  • Resource (.tres) — typed, editor-friendly, weak for bulk text
  • CSV — great for tables, poor for nesting
  • JSON — best balance for narrative graphs

Step 3: Design the Script Structure

3.1 Minimal Node

Create data/dialogues/dialogue.json:

{
  "village_chief_start": {
    "character": "Village Chief",
    "text": "Young traveler, you made it. The forest east of the village has been restless—can you investigate?",
    "next_node": "END"
  }
}

3.2 Field Meanings

  1. Root object → Godot Dictionary
  2. Dialogue ID (village_chief_start) — stable node name, not array index
  3. character — speaker name
  4. text — line body
  5. next_node — next ID; END closes the conversation

3.3 Branching

{
  "village_chief_start": {
    "character": "Village Chief",
    "text": "Young traveler, you made it. The forest east of the village has been restless—can you investigate?",
    "choices": [
      {
        "text": "I'll go now.",
        "next_node": "accept_quest_forest"
      },
      {
        "text": "I need more preparation.",
        "next_node": "refuse_quest_forest"
      }
    ]
  },
  "accept_quest_forest": {
    "character": "Village Chief",
    "text": "Excellent! Take this rations—travel safe.",
    "next_node": "END"
  },
  "refuse_quest_forest": {
    "character": "Village Chief",
    "text": "Then prepare well—the village is counting on you.",
    "next_node": "END"
  }
}

choices (optional array): each entry has text and next_node.

Rules: if choices exist, skip next_node on that node; linear nodes use next_node.

Step 4: Full Schema (Reference)

Aligned with the course project godot_simple_arpg_demo.

4.1 Dialogue Node

{
  "node_id": {
    "character": "name or localization key",
    "text": "line or localization key",
    "choices": [ ],
    "next_node": "next_id or END",
    "condition": { },
    "action": { },
    "actions": [ ]
  }
}

4.2 Choice

{
  "text": "label or key",
  "next_node": "next_id",
  "condition": { },
  "action": { },
  "actions": [ ]
}

4.3 Condition (later lessons)

{
  "quest_status": {
    "id": "quest_id",
    "status": "can_accept|in_progress|ready_to_turn_in"
  }
}

Or:

{
  "has_item": {
    "id": "item_id",
    "amount": 1
  }
}

4.4 Action (later lessons)

{
  "type": "give_item|start_quest|affinity_change|give_reward",
  "id": "item_or_quest_id",
  "amount": 1,
  "npc_id": "npc_id",
  "value": 10
}

4.5 Production Example (Localization Keys)

{
  "village_chief_start": {
    "character": "CHARACTER_VILLAGE_CHIEF",
    "text": "VILLAGE_CHIEF_GREETING",
    "choices": [
      {
        "text": "VILLAGE_CHIEF_CHOICE_ACCEPT",
        "next_node": "accept_quest_forest",
        "condition": {
          "quest_status": {
            "id": "chief_forest_quest",
            "status": "can_accept"
          }
        }
      },
      {
        "text": "VILLAGE_CHIEF_CHOICE_REFUSE",
        "next_node": "refuse_quest_forest",
        "condition": {
          "quest_status": {
            "id": "chief_forest_quest",
            "status": "can_accept"
          }
        }
      }
    ]
  },
  "accept_quest_forest": {
    "character": "CHARACTER_VILLAGE_CHIEF",
    "text": "VILLAGE_CHIEF_ACCEPT_REPLY",
    "actions": [
      { "type": "give_item", "id": "bread", "amount": 2 },
      { "type": "start_quest", "id": "chief_forest_quest" }
    ],
    "next_node": "END"
  }
}

Ship builds use keys instead of raw prose; localization chapters cover the pipeline.

Step 5: Design Principles

5.1 Unique IDs

Good: village_chief_start, accept_quest_forest, boss_battle_intro. Bad: node1, dialogue, test.

5.2 Extensibility

  • Conditions via condition
  • Actions via action / actions
  • Localization via keys
  • Optional metadata for extras

5.3 Backward Compatibility

New fields optional; missing fields get sane defaults; old files keep working.

Step 6: Hands-On

  1. Create data/dialogues/
  2. Add dialogue.json
  3. Start from the branching sample and rewrite for your game
  4. Validate JSON in VS Code ( brackets, quotes, trailing commas )
  5. Sanity-check graph: every next_node resolves; no accidental cycles

Exercise and Completion Check

Add a two-choice node to the sample JSON and trace each destination on paper.

Done when: The JSON parses and each non-END destination exists in the file.

Lesson Summary

  • Data-driven separation of content and code
  • Dialogue node schema and branching rules
  • Principles: IDs, extension points, compatibility

Schema Quick Reference

  • character (string, required) — speaker or key
  • text (string, required) — line or key
  • choices (array, optional)
  • next_node (string) — required when no choices
  • condition, action, actions (optional)
